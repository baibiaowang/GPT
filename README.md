# 通用表格整理转换器 · GPT 专用仓库

这是 GPT 专用的通用表格整理转换器 App 开发仓库。

## 产品最终定位

本 App 不是股票专用 App，也不是业务判断 App。

它本质上只是一个：

> 为了方便阅读，把外部表格数据整理、转换、筛选并以适合手机阅读的方式展示出来的通用表格整理转换器。

最终设计目标是：同一套 App 能适应各种结构的表格，而不是针对某一种表格不断增加硬编码字段。

股票数据只是当前使用场景之一。任何后续表格都应尽量通过“表头 + 行数据 + 单元格值”驱动界面，而不是要求程序理解某个业务领域。

## 最终页面模型

### 首页：总表格

首页就是整张表格的整理阅读视图。

它显示当前表格的全部行，但为了手机阅读，可以只显示若干个适合快速浏览的表头和对应单元格内容。

这里的“若干表头”由数据或布局配置决定，不应永久写死为股票名称、判断分类、公告时间。

首页的核心关系只有：

> 表头 → 多行数据 → 单元格内容

### 类型：按某个表头筛选

“类型”不是股票业务功能。

它表示：选择某一个表头，然后查看这个表头下面存在的各种不同取值，并筛选出对应的所有行。

例如某张表有“地区”表头，那么“类型”可以按“地区”筛选；如果另一张表有“部门”表头，就可以按“部门”筛选。

因此类型页最终应由可筛选表头 + 该表头的值集合动态产生，而不是固定依赖 category。

### 结论：按某个表头筛选

“结论”和“类型”本质相同，只是默认针对另一类适合做结果汇总的表头。

最终设计应支持：选择某一个表头 → 自动列出该表头所有实际存在的取值 → 点击某个取值 → 查看匹配的全部行。

不能把“利好 / 不利 / 否决”等业务词永久写死为 App 的结论体系。

### 详情页：完整的一行

详情页本质上不是“股票详情页”。

它就是表格中某一行数据的完整展示。

只是为了手机阅读，对这一行使用稍微有一点样式和层次。

因此详情页应该能够展示该行的全部表头和对应单元格，不要求固定 8 个字段。表格增加字段后详情页自动增加，表格减少字段后详情页自动减少。

### 点评：本地附加筛选条件

点评不是数据表本身的字段。

它是用户针对某一行额外添加的本地信息。

> 原始表格的一行 + 本地点评

然后通过“点评”筛选条件重新找到这些被用户加过点评的行。

点评数据应与原始表格解耦；当远程表格更新、某一行暂时不再出现时，用户已经保存的点评仍应可以找到并查看。

### 收藏：本地附加筛选条件

收藏也不是原始表格字段。

它是用户针对某一行增加的本地标记。

> 原始表格的一行 + 本地收藏标记

“收藏”页面只是筛选出已经被用户本地收藏的行。

收藏必须与原始数据更新解耦：表格更新后，只要能够识别原来那一行，就应该继续保留用户的收藏关系。

## 核心设计原则

### 1. 数据驱动，而不是业务驱动

程序首先认识的是：表格 → 表头 → 行 → 单元格。

而不是：股票 → 股票代码 → 股价 → 判断分类 → 公告时间。

股票字段只是某一种表格的字段。

### 2. 表头动态化

表头应该来自数据本身或者明确的数据布局配置。

程序不应假设任何固定业务字段一定存在。

### 3. 筛选动态化

筛选器应该可以从实际表头中生成。

程序不应该把 category、conclusion 等业务字段写死成系统级概念。

### 4. 详情动态化

详情页应完整展示“当前这一行”的所有字段。

任何表格增加、减少、改名字段，都不应要求重新开发页面结构。

### 5. 本地附加信息与原始数据分离

收藏、点评以及未来可能增加的本地标记，都属于 App 自己维护的附加数据。

原始表格负责提供原始行数据；App 负责维护本地附加信息。

### 6. 手机阅读优先，但不能破坏表格关系

样式可以是卡片、标签、折叠和其他适合手机阅读的形式，但本质关系不能变：

> 一个表格 → 多个表头 → 多行 → 每行多个单元格

### 7. 允许不同格式的数据源

最终应尽量兼容常见表格输入，例如 JSON、Markdown 表格、TSV / 制表符表格，以及其他可以明确识别表头与行列关系的结构化文本。

不同数据源进入 App 后，统一转换为内部“通用表格模型”。

## 通用内部模型（最终目标）

最终内部数据模型应尽量接近：

    Table
     ├─ columns[]
     │    ├─ key
     │    └─ label
     └─ rows[]
          └─ cells[]
               └─ value

本地附加数据独立维护：

    LocalAnnotations
     ├─ favorites
     └─ comments

这样才能真正做到“一套 App，适应多种表格”。

## 2.0.0 最终实现状态

2.0.0 已按本总纲完成核心架构迁移：

- App 的第一对象是 Table，而不是 Stock。
- 每个表头由 columnId 编号管理：001、002、003……
- 每个表头下的实际取值由 valueCatalog 编号管理：V001、V002……
- 每行由 rowId 标识，单元格只保存 columnId + value。
- 首页是总表格整理视图，只显示配置的若干表头和对应单元格。
- 类型是选择某个表头后，对该表头全部实际取值的动态筛选。
- 结论与类型采用同一机制，不固定任何业务枚举。
- 详情是当前 Row 的全部字段展示，并保留适合手机阅读的样式。
- 收藏、点评均为本地附加信息，以 tableId + rowId 关联，并保存行快照。
- 数据源支持 JSON 表格、JSON records、Markdown 表格、TSV、CSV 等可识别的二维表格文本。
- 股票数据只是当前一个表格实例，不能作为核心模型的特殊分支。

2.0.0 发布验收时，重点检查“换成商品表、人员表、项目表、财务表是否无需修改页面代码”。只有继续满足该条件，才视为符合最终设计目标。
